# dev97 ModelProvider replacement acceptance

Status: accepted implementation subset. Frozen regression, same-reviewer closure,
independent installations, repaired application and original-version compatibility
passed. Final document/package/local-delivery receipts are recorded separately;
full capabilities and actual quality/adoption remain open.

## Scope and authority

The existing immutable runner gains `model-provider/v1`: core P01–P10 and explicit
tools P01–P16. Generic finite JSON ModelResponse and optional extension ports
remain distinct from vendor text protocols. Existing K/S/Facts catalog/report
bytes and the five-scenario model-check evaluator remain preservation gates.

An independently editable SQLite supplier implements the async model port and
records actual request/response observations. It does not deduplicate model
calls or decide Run state. Configured Agent, current-source RAG, rule DAG Plan
and Supervisor Team retain original Local/Action/approval/receipt/budget authority.
The application requires actual business source/tool/member evidence at completion.

Completed-invalid response encoding and live provider method/source mutation
are checked at original receiving/adoption boundaries. Original received completion
and known cost must survive rejection. Published provider identities, native
methods and persisted default manifests remain unchanged; live method pins do not
certify implementation equivalence across rebuild/restart.

## Explicit-resume compatibility ruling

The original [recovery guide](../../docs/recovery-guide.md) permits an explicit
resume to create a new separately reserved model Attempt on the original Action
and snapshot, retaining the old unknown hold. This increment preserves that
behavior rather than adding a blanket unknown-model guard. Read-only reconnection,
status and diagnostics do not redispatch. Lost response after process death may
still be persisted as abandoned executing/unreceived with reserved cost before
an authorized normalization step; that is not a fabricated outcome_unknown record.

## Acceptance evidence

One fresh independent review reproduced six P2s: equal bound receivers bypassing
live method pins, a marginal nesting depth losing known completion, cancellation
raised by lazy disposal, P01 leaking invalid lazy output, a real business receipt
for the wrong requested incident, and generated app closure preceding the
original Runtime drain. The original authors repaired these boundaries in
two independent lanes; the same reviewer closed all six with 33 fresh zero-skip
checks, including eight actual historical-response processes. The first candidate's 192 installed configuration
combinations are preliminary evidence; they do not close these findings or
establish final package acceptance.

Root ruling: newly returned completed evidence is limited to 128 nested JSON
containers before recursive capture. Excess depth must remain a completed,
received-invalid response with settled cost. This trades arbitrary JSON nesting
for deterministic durable capture, preserves historical received records, and
avoids interpreter-stack-dependent unknown outcomes. The rule applies at the
shared response capture boundary rather than changing native model identities.
