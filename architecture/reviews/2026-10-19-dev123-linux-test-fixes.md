# dev123：Linux Artifact 与 SQLite 测试修复复验

日期：2026-10-19。对本地 `c4fe423` 的两项 Linux 发现进行归因、测试修复与同限制重验。不增加产品功能；函数指纹专项及 S2 后置，不推送。原[首轮失败记录](2026-10-19-dev123-linux-basic-validation.md)及其制品保持不变。

## 归因与修正

**两项均为测试／夹具问题，未证实产品缺陷。442 个产品文件与原 dev123 wheel 清单逐字节一致。**

| 发现 | 原因 | 本批修复 |
| --- | --- | --- |
| Python 3.11 并行 Artifact.put=2，原断言要求1 | 各独立节点 frame 都可先观察内容不存在，再首次调用同一个内容寻址后端；产物存储去重不承诺跨 frame 全局单次调用。原数据库只有一份产物、8个不同业务效果键 | 用实际调用的 `(run_id, workflow_node, artifact_id)` 唯一性关联原派发事件；分别确认每 frame 不重复调用、最终只有一个完整原始产物、业务工具8次与摘要4次。直接共用的 FileArtifact／RelevantDataContext 恢复测试使用同一断言 |
| Python 3.13 的12个 SQLite ResourceWarning | 原父测试 `with sqlite3.connect(...)` 只管理事务，未关闭连接；分配追踪全部指向原 composite 测试223行 | 读取使用 `contextlib.closing`，夹具写入用 `with closing(connection) as db, db:` 保持先提交／回滚后关闭；夹具负责关闭借给 Engine 的 ArtifactStore，保持 `os._exit(77)` 的真实死亡窗口，不屏蔽警告 |

通过测试专用 rendezvous 让两个原始 parallel frame 都先观察 NotFound，保留三个受控场景：

- 两个摘要响应／采纳窗口：崩溃前真实后端各进入一次，合计2次；恢复后仍为2，不以内容去重掩盖重复调用。
- artifact_commit 窗口：两个派发记录已提交，但只有一个真实后端调用进入并持久化后进程死亡。恢复可读回相同产物，另一个 frame 不需要进入 put；断言1次，避免将派发数误当调用数。
- 实际调用按任务 ContextVar 关联 frame，入口先持久记录计数与身份；缺失身份也记录无效元组，随后才抛错，最终断言拒绝该元组。这样即使产品读回路径捕获了异常，也不能漏掉错误重试。独立只读复核发现的这一 P2 已关闭；另有定向入口审计证据。

这些只增强夹具的可观察性及恢复断言，不修改执行器、调度、内容寻址身份或执行权威。
