# 文档维护指南

[文档目录](README.md) · [贡献指南](../CONTRIBUTING.md)

文档面向首次使用者、应用开发者和框架贡献者。优先帮助读者完成任务，再提供 API、设计与验证证据。当前以中文讲解为主，代码标识和协议名保留原文；英文专题可继续维护，避免添加未经同步核对的平行译本。

## 文档放在哪里

| 内容 | 位置 | 维护方式 |
| --- | --- | --- |
| 项目定位、最短安装、最小示例 | [根 README](../README.md) | 保持简短，通过链接进入专题 |
| 分类导航与学习路径 | [docs/README.md](README.md) | 新增专题时同步加入分类 |
| 首次使用与安装 | [getting-started.md](getting-started.md)、[installation.md](installation.md) | 从干净环境核验命令、预期状态与下一步 |
| 概念解释 | [concepts.md](concepts.md) | 解释术语及关系，链接具体用法 |
| 功能指南与参考 | `docs/<topic>.md`、[API 参考](api-reference.md) | 先给默认用法，再写配置、扩展及限制 |
| 可运行源码示例 | `examples/` 与[示例索引](../examples/README.md) | 标注工作目录、依赖、离线／真实模型和预期输出 |
| 支持状态与路线 | [实现清单](implementation-status.md)、[剩余能力](remaining-work.md) | 保持当前事实与待验收事项的统一入口 |
| 版本与验收证据 | [CHANGELOG](../CHANGELOG.md)、`architecture/reviews/` | 绑定版本、配置、制品及实际验证范围 |
| 设计、契约与计划 | `architecture/`、`docs/superpowers/` | 保留过程材料，通过[历史索引](project-history.md)进入 |
| 历史入口快照 | `docs/archive/` | 标注日期和历史性质，修正移动后的相对链接 |

不把每批验收数字和开发代号追加到首页。保留现有专题路径，避免让外部链接失效；确需迁移时，在旧路径留下新入口并检查入链。

## 一篇功能指南应包含什么

1. 说明适用场景、依赖、执行后端与支持边界。
2. 给出最小可运行命令，明确执行目录、占位符和环境变量。
3. 描述预期结果，以及等待审批、未知效果或错误时的下一步。
4. 提供可替换组件、配置身份、生命周期和原任务恢复约束。
5. 链接 API／契约及验证记录；把历史细节留在对应记录中。

声明式片段或需已有对象的代码应标注前置条件。模板名称、CLI 参数、可选 extra 和导入符号应与代码一致。密钥使用环境变量占位，示例选择临时或 `.ralf/` 数据目录。

## 如何验证文档改动

- 检查新增和修改页面的相对路径、标题锚点与代码围栏，确保从 README 和目录能找到新文档。
- 运行受影响的最小示例；离线示例不调用收费模型或生产工具。审批演示保留显式检查与批准步骤。
- 若修改安装或打包内容，检查源码分发包是否包含需要的文档；wheel 的包内模板与仓库示例分别说明。
- 使用 `git diff --check` 检查空白；仅修改说明和导航时无需全量运行产品测试。改动执行行为时按[贡献指南](../CONTRIBUTING.md)执行相关回归与检查。
- PR 中记录执行的命令、结果与未覆盖范围。历史证据不改写为本轮验证结果。
