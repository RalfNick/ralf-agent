## 定位依据与边界

- 原失败数据库显示两个独立并行 node frame 各有一次同内容产物派发／核验，Artifact 库一条产物。现有内容寻址 put/get 契约不保证跨 frame 全局只调用一次 put；先用受控并发证明，不先改执行器或调度。
- Python 3.13 的 12 个连接分配已定位到测试父进程读取 business.sqlite。修复该夹具及直接共用场景的资源所有权，不屏蔽警告。
- 若仅测试问题，继续使用原 dev123 wheel；修正后的测试输入单独归档，不覆盖原 wheel、sdist、Linux 失败记录或验收结果。
- 保持 2 CPU／2 GiB／无额外 swap、相同三幅 Linux ARM64 镜像，3.11→3.12→3.13 串行；测试前断网。保留原 308 node，加受控并发与直接受影响场景；精确增量分别记录。
- 只跑定向和这套基础矩阵，不启动全量中的后置函数指纹／S2，不改版本／Schema／执行权威，不推送。

## 执行步骤

1. 构造两节点都先观察到 NotFound 的受控并发，确认原“全局 put=1”断言可稳定失败；保留 RED。核对每 frame 意图、派发、回执、业务效果键和最终原始内容。
2. 修正全局计数假设为原契约的检查：每个独立 frame／artifact 仅派发一次，单独记录真实调用身份、确认每次调用都有派发且同 frame 不重复调用（崩溃时可存在尚未进入方法的派发）；单份持久产物及原内容、业务效果各一次、恢复不再派发已确认写入。关闭测试与进程夹具拥有的 SQLite／Artifact 资源，保留真实进程死亡窗口。
3. 原 wheel 配合冻结的新测试输入，在相同镜像和限制下串行重验三版本原矩阵、新并发回归及直接共用夹具的场景；收集 JUnit、依赖、内存／CPU及自有关闭证据。
4. 独立复核完整本批差异和证据，更新当前状态与新验收记录；原失败不可改写。仅保存本地改动和证据，不推送。
