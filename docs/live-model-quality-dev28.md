## 失败原因与运行事实

六个修复样本都正确输出了 cause／fix 代码和 resolved，但只读取了诊断，没有提出 apply_fix，没有进入写审批，业务写入为零。因此最终 JSON 答案匹配仍判失败。报告中的 Run state=succeeded 表示 Agent 得到了合法终答；业务评分器独立读取实际服务和动作，才判断目标是否完成。

这暴露了默认应用验证的缺口：Schema 只能校验结构，不能证明业务效果。后续需要显式业务 Verifier／完成证据约束和可靠的默认 Agent 组合；不能用答复文字作为效果回执。本轮没有修改指令、冻结任务、成功 oracle 或失败记录来提高成绩，也没有对子集进行额外付费复测。

五个缺输入／拒绝样本各跑两次，均符合期望且没有业务写入。重复提交、重建 Engine 后返回原回执和终态；修复案例没有产生写动作，因而本轮真实模型试验不能证明模型驱动的写审批／写恢复质量。运行内核的实际审批恢复由独立离线安装包及原有故障契约验证。

## 范围案例与证据限度

新绑定案例共享两个客户端，分别在 red／blue Facts namespace 放置不同策略，在 red／blue Knowledge namespace 放置不同文档。四个独立 Agent 使用同一真实 Provider，在固定范围中复制正确策略；两个知识案例同时返回正确 fixture:// 来源 URI。该试验验证有限的来源值／引用提取及装配使用，不证明宽泛的语义检索、复杂问答、记忆真值或自动记忆质量。

这不是与 AgentScope／LangGraph 的对等 benchmark，也不能与 dev21 的不同模型／协议／指令阶段拼接成一个高分结果。完整规划、真实生产数据、长上下文、复杂 RAG、业务 Verifier 和独立开发者采用仍需各自验收。

模型试验发生于本轮最终审查修复前。后续修复的是委托客户端身份守卫和 Facts 分页；本试验使用无分页 Facts 与原知识视图，稳定客户端的请求内容没有修改。修复后完成运行契约、完整回归和安装包验证，没有进行额外付费复测。
